## 二、关键核实：用户已开通的"经营版收款"能力对照（2026-08-11 调研结论）

> 用户已开通微信 + 支付宝"经营版收款"。但**"经营版收款"≠"可自动开通的支付接口"**，必须分清：

| 已开通的东西 | 有没有 API 接口 | 能不能自动回调到账 | 结论 |
|--------------|-----------------|-------------------|------|
| 微信「经营收款码」/「商家收款码」（扫收款码转账） | ❌ 无 API | ❌ 无回调，只能手动看收款记录 | **不能**用于自动开通 |
| 微信支付「商户号」Native/JSAPI 支付 | ✅ 有 API | ✅ 支付成功回调 notify_url | **能**自动开通 |
| 支付宝「商家收款码」（静态码） | ❌ 无 API | ❌ 无回调 | **不能**用于自动开通 |
| 支付宝「当面付/手机网站支付」（开放平台签约） | ✅ 有 API | ✅ 异步通知 notify_url | **能**自动开通 |

> **结论：用户现有的"经营版收款"大概率是收款码（无 API），方案 B 自动开通需要另走正规商户通道（微信商户号 / 支付宝当面付签约）。这不是"重开"，而是在现有收款基础上补 API 能力。**

## 三、前置条件（必须先解决，否则支付接不上）

| # | 条件 | 说明 | 状态 |
|---|------|------|------|
| P-1 | **微信支付商户号** | 需个体工商户营业执照（用户已有，但两年多没营业——**需先确认执照状态**：被吊销/注销则不可用，经营异常可补年报恢复）+ 法人身份证。费率 0.6%。**关联需微信认证服务号（认证费 300 元/年）**，H5 支付还需 18 类目审核 | ⛔ 待办 |
| P-2 | **支付宝手机网站支付签约** | **个人账号可开通**，需已备案 H5 域名（未上线可先交 3 张页面截图：首页/服务页/支付页，30 天内上线提额）。费率 0.6% | ⛔ 待办 |
| P-3 | **备案域名** | 支付宝 H5（return_url/notify_url）+ 微信 H5 支付域名**都必须用已 ICP 备案的 HTTPS 域名**（2026 年未备案拦截率极高）。pages.dev 无法备案 → 需注册备案域名（约 60 元/年 + 备案 1-2 周） | ⛔ 未办 |
| P-4 | **商户证书/密钥** | 支付宝 RSA2 应用密钥（开放平台创建应用后生成）；微信 API v3 密钥 + 商户私钥证书 | ⛔ 未办 |
| P-5 | **收款结算账户** | 微信个体户可结算到法人个人银行卡（无需对公账户）；支付宝结算到支付宝余额 | ⛔ 待办 |
| P-6 | **APP 跳回验证** | Capacitor WebView 跳支付宝 APP 支付后回跳 return_url：需真机验证 alipays:// scheme 唤起与 WebView 会话保持（Capacitor 壳 + pages.dev 场景） | ⛔ 待验证 |

> **结论：P-1/P-2（支付通道）+ P-3（备案域名）是硬门槛。备案域名 1-2 周等待期最长，建议最先启动；支付宝当面付个人可先通，微信商户号后补。**

## 四、技术方案选型（v3：H5 网页支付）

### 用户拍板形态
**H5 网页支付**：用户在 APP 会员中心点「立即开通」→ 跳转浏览器/支付宝收银台 → 支付 → 付完自动跳回 APP。不做 APP 原生支付（无需原生 SDK/插件，纯网页实现）。

### 方案对比（基于 Cloudflare Pages Functions 无服务器架构）

| 方案 | 支付方式 | 用户体验 | 技术复杂度 | 资质门槛 | 适配场景 |
|------|----------|----------|-----------|----------|----------|
| **A. 支付宝手机网站支付（WAP，推荐主通道）** | 网页跳支付宝收银台 → 自动唤起支付宝 APP → 付完回跳 return_url | 最顺滑，无需扫码 | 低（纯网页表单跳转） | **低：个人账号可开通**（需已备案 H5 域名；未上线可先交 3 张页面截图审核，30 天内上线） | 完美契合「点开通→跳转→付完回来」 |
| **B. 微信 H5 支付** | 网页唤起微信客户端支付 → 付完回跳 | 顺滑 | 中 | **高：需已认证服务号（300 元/年）+ 商户号 + 备案域名 + 18 类目开放** | 用户微信使用率高，必须做；资质最重 |
| C. 微信 Native 扫码 | 网页显示二维码，微信扫 | 需另一台手机/截图扫 | 中 | 高：需商户号+备案域名 | 兜底备选（用户微信场景） |
| D. 支付宝当面付扫码 | 网页显示二维码，支付宝扫 | 需扫码 | 中 | 低：个人可签 | 已被 A 替代（A 体验更好） |
| E. 第三方聚合 | 封装微信/支付宝 | 一般 | 低 | 低（跑路/风控风险） | 不推荐正式使用 |

**推荐：A 支付宝手机网站支付（H5 跳转）先行 + B 微信 H5 支付后补（双通道）**。
微信 H5 是最终目标（用户微信使用率高），但其资质最重（认证服务号 300 元/年 + 商户号 + 备案域名 + 类目审核），放在支付宝通道跑通后推进；在微信 H5 开通前，微信侧可用 C（Native 扫码）临时兜底。

### H5 支付核心机制（支付宝为例）

```
用户选档位 → 点「立即开通」
    ↓
前端 POST /api/pay/create {phone, planId, deviceId}
    ↓
云函数: 校验登录 + 生成订单号 + 调支付宝 alipay.trade.wap.pay（手机网站支付，RSA2 签名）
    ↓
返回: 收银台 URL + 订单号
    ↓
前端跳转收银台（自动唤起支付宝 APP / 网页收银台）→ 用户支付
    ↓
支付完成 → 支付宝 POST 异步通知 /api/pay/notify（验签+幂等，唯一可信来源）
    ↓
云函数: 给该账号 vipUntil += 对应天数（终身=2100年）→ 写 account_
    ↓
支付宝同步跳转 return_url → 前端轮询 /api/pay/status {orderNo} → 成功 → 弹「开通成功」→ 刷新会员中心
```

**关键设计点（H5 支付专属）**：
| 点 | 设计 |
|----|------|
| return_url vs notify_url | return_url（同步跳转）**只做前端展示**，不可信；notify_url（异步回调）**唯一可信支付结果**，后端验签+幂等 |
| 幂等 | 回调幂等（同一订单只加一次 VIP，用订单号去重） |
| 防刷 | 下单前校验登录 + 档位金额与商品ID一一对应（防止改价） |
| 回调安全 | 支付宝 RSA2 验签 + 回调参数白名单 |
| 订单过期 | 订单 2 小时有效，超时取消 |
| 会员叠加 | 已 VIP 用户续费 = 在原 vipUntil 基础上加天数（不是重置） |
| 终身卡 | vipUntil 设 2100-12-31（或加 isLifetime 标记） |
| 退款 | 暂不做在线退款（个人主体可先说明"联系管理员人工处理"） |
| APP 跳回 | 支付宝 APP 付完自动回 return_url；WebView 环境需验证 alipays:// scheme 唤起（Capacitor 壳支持） |

### 数据存储（沿用现有 KV）

| KV key | 内容 |
|--------|------|
| `pay_order_<orderNo>` | 订单：phone/planId/amount/status(created/paid/closed)/createdAt/paidAt |
| `account_<phone>.vipUntil` | 已存在，续费时叠加 |

### 前端改动点

1. 会员中心「立即开通」→ 调支付（替换现在 toast）
2. 新增支付弹窗/页面：二维码展示 + 轮询状态 + 成功/失败/过期三态
3. VIP_TEST_MODE=false 开关（正式收费时切，7 处拦截自动生效）

## 四、老用户政策（测试期 → 正式收费过渡）

**这是最容易得罪人的环节，建议二选一（或组合）：**

| 方案 | 内容 | 优缺点 |
|------|------|--------|
| **方案 1：老用户赠期** | 测试期注册的用户，正式收费后**自动送 1 个月 VIP**（按注册时间） | 好口碑；成本低（1 个月） |
| **方案 2：老用户感恩价** | 首月 0.1 元 / 年卡 5 折（限测试期老账号） | 有收入又有诚意 |
| **方案 3：邀请抵扣** | 正式收费时，之前邀请成功的每个好友 = 减 5 元（已有邀请记录数据） | 拉新和收费联动，最有增长价值 |

> 我的建议：**方案 1 + 3 组合**——老用户送 1 个月 + 邀请记录折现，既安抚老用户又激励拉新。

## 七、风险与对策

| 风险 | 对策 |
|------|------|
| 营业执照两年没营业 → 被吊销/经营异常，微信商户号申请被拒 | ①先查执照状态（国家企业信用信息公示系统）；②经营异常→补年报免费恢复；③已吊销→重办个体户执照（线上 3 天，约 0 元）或支付宝先走个人当面付额度（单笔≤2000） |
| 备案等待期长（1-2 周） | 提交备案后立即用支付宝沙箱联调 + 前端支付弹窗开发并行；备案下来即切换正式环境 |
| 微信认证费 300 元/年（需关联小程序/服务号） | 属微信硬性要求，接受；或先用支付宝通道收款，微信通道评估后再开 |
| 支付回调丢单 | 前端轮询兜底 + 每日对账脚本（拉取支付宝/微信账单比对订单状态） |
| 用户支付后 VIP 没到账 | 回调幂等 + 前端「我已支付未到账」申诉入口（管理员手动补发） |
| 用户扫码习惯不同（有人只认微信） | 双通道并行：支付宝先上，微信后补；测试期免费过渡不造成付费流失 |

## 八、结论

- **支付形态（v3 用户拍板）**：H5 网页支付——点开通 → 跳转浏览器/支付宝收银台 → 付完自动回 APP，不做 APP 原生支付（纯网页实现，无需原生 SDK）
- **用户已有的"经营版收款"（收款码）无 API，不能直接自动开通**；方案 B 需补正规商户通道：**支付宝手机网站支付（个人可签、最快）+ 微信 H5 支付（需有效执照 + 认证服务号 + 备案域名 + 类目审核）**
- **最大瓶颈不是技术，是资质**：备案域名（1-2 周）+ 营业执照状态（需确认/恢复）+ 微信认证服务号（300 元/年）
- **建议**：①今天就去查执照状态（决定微信通道可行性）；②立即注册备案域名提交备案；③支付宝 H5 签约 → 2 周内支付宝通道上线；④微信 H5 后补 → 双通道齐备（微信开通前可用 Native 扫码兜底）
- **过渡期**：保持测试期免费跑通拉新，正式收费用「老用户送 1 月 + 邀请折现」平滑过渡
- **前端改动**：会员中心「立即开通」→ 支付跳转（H5 收银台）+ 轮询 + 三态 + VIP_TEST_MODE 开关切换，改动量约 1 天；**P-6 APP 跳回需真机验证**（Capacitor WebView 唤起支付宝 APP 后回跳）
